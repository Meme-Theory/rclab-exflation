# Ainulindalë Console

A live browser exhibit of the Exflation knowledge base — the D_K spectrum as an
instrument, the Paasch spiral as a p-value, the session graph as a story, the
equation atlas as a drill-down.

Six braided views share one selection bus: click a Dirac mode in *The Bell*,
its eigenvalue pops into the right-rail inspector. Click a variable chip in the
*Equation Atlas*, the inspector jumps to the underlying canonical constant with
full session/gate provenance. Open the *Library* and every one of 1,241 display
equations is searchable with lazy KaTeX rendering. Scrub the *Session Ring*
slider, watch the probability trajectory at the bottom rewind.

Views:

- **The Bell** — 1,620-point representative D_K spectrum on a ring, τ-slider
  lifts degeneracies at the fold, click-to-ring any mode, strike fires the
  ω_B2 / ω_B1 / ω_B3 chord.
- **Paasch Spiral** — 6 mass-quantization rays; drag φ to watch sequence
  alignment collapse + p-value explode.
- **Equation Atlas** — 10 hand-curated story cards with clickable variable
  chips that drill into real canonical constants.
- **Library** — full 1,241-equation browsable grid, search-filtered, lazy
  KaTeX via IntersectionObserver (scrolling is instant).
- **Session Ring** — 100 real sessions, area-grouped with timeline scrub.
- **Drill to Bedrock** — target equation → cited theorems/gates → canonical
  constants dependency tree.

Right-rail inspector is tabbed (Gates · Constants · Theorems · Closed ·
Open · Researchers) with a search filter on every tab. Bottom strip shows
the probability trajectory + equation-wordmap.

## Quick start

```bash
# Regenerate live data (reads tools/knowledge.db + canonical_constants.py)
"phonon-exflation-sim/.venv312/Scripts/python.exe" tools/viz/console/build_data.py

# Serve (any static-file server works; Python's built-in is fine)
python -m http.server 8000 --directory tools/viz/console
```

Open <http://localhost:8000/index.html>. No build step, no Node, no bundler.

## Files

### Console stack (consumed by `index.html`)

| File                | Role                                                                                   |
|---------------------|----------------------------------------------------------------------------------------|
| `index.html`        | Shell: tabs, main stage, right-rail inspector, bottom strip. Loads KaTeX from CDN.     |
| `styles.css`        | Design tokens (oklch palette, JetBrains Mono, brass accent), view-specific CSS.       |
| `views.js`          | All five view builders + shared selection bus (`window.BUS`).                          |
| `data.js`           | **Live data** — regenerated from the knowledge base by `build_data.py`.                |
| `data.seed.js`      | **Hand-curated fallback** — the original design-tool slice. Never regenerated.         |
| `build_data.py`     | Generator. Reads SQLite DB + Python canonical constants, emits `data.js`.              |

### Sidecars (JSON outputs consumed by downstream views + the meme-engine-web Astro build)

Four standalone JSON sidecars sit next to `data.js`. Each is produced by its own builder script in this directory and serves a specific cross-cutting visualization concern. The sidecars are **not** generated by `/weave --update` — they are refreshed manually after the underlying graph (`knowledge.db`) changes.

| Sidecar (JSON)              | Builder                          | Purpose                                                                                                                                                                            | Size (typical) |
|-----------------------------|----------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------:|
| `master_inventory.json`     | `build_master_inventory.py`      | Falsifier-watchlist Gantt rows. Parses `sessions/framework/registry/falsifier-watchlist.md`; per row emits `(prediction_id, observable, framework_prediction, detector, t_low, t_high, σ_distance, xcorr_class, evoi_rank, status, fisher_sha)`. EVOI rank drives Gantt sort. | 4 KB |
| `plan_state_diff.json`      | `build_plan_state_diff.py`       | Plan-vs-state Δ(P, S) Lyapunov diff per session. Walks every session with both a plan corpus (`sessions/session-plan/session-{N}-plan-*.md`) and a verdict ledger (`computations/session-{N}/s{N}_gate_verdicts.txt`); extracts the plan-DAG vs realized-DAG (symmetric-diff edges classified PLANNED_NOT_REALIZED / REALIZED_NOT_PLANNED), missing/extra gates, deviation count. | ~70 KB |
| `theorem_genealogy.json`    | `build_theorem_genealogy.py`     | Structural-theorem cross-track graph. Two node sources combine: (1) S85+ slot×track workshop files (`session-{N}-s{slot}-{slug}-{track}.md`) — multiple tracks proving the same structural theorem with different machinery, generating `cross_track` edges; (2) quality-filtered `proven_N` rows from `knowledge.db::theorems`. Edges: `cross_track` / `cites` / `depends_on`. | ~57 KB |
| `chain_of_custody.json`     | `build_chain_of_custody.py`      | Per-anchor bidirectional BFS pre-compute. For 3,000+ anchor entities (gates, constants, theorems, mechanisms, sessions, researchers), pre-computes upstream/downstream chains at depth=4, top_K=20 per level, with each chain edge tagged by one of four lenses: `authorship` / `citation` / `custody` / `logical`. The "red string on the wall" data for Genealogy view; lens-tagged so the frontend can re-color or hide subgraphs at render time. | 5.1 MB |

## Switching between live and seed data

- **Live (default):** `<script src="data.js"></script>` in `index.html`.
- **Seed:** change the tag to `<script src="data.seed.js"></script>`.

The schemas match; everything else stays the same. The seed is the verified
baseline — useful if a DB change breaks something in the generator.

## What the generator pulls

```
CONSTANTS          canonical_constants.py  → all 194 public scalars + seed fallback
                                              (~209 total), tagged by heuristic
THEOREMS           knowledge.db::theorems  → quality-filtered live + 18 seed IDs (~104)
GATES              knowledge.db::gates     → pre-S81 narrative + S81+ Level-3 audit,
                                              interleaved (~131 across 40+ sessions)
CLOSED_MECHANISMS  knowledge.db::closed_mechanisms → all real mechanism closures (~350)
OPEN_CHANNELS      knowledge.db::open_channels     → all surviving channels (~350)
SESSIONS           knowledge.db::sessions  → all 100, area inferred from text
EDGES              derived                 → continues/bridges from session adjacency
REAL_EDGES         knowledge.db::edges     → 63 typed gates→constants reproducibility edges
TRAJECTORY         knowledge.db::probability_trajectory → parsed panel values (~100)
RESEARCHERS        knowledge.db::researchers → all 39 by citation_count, hue by domain hash
EQUATIONS          data.seed.js            → 10 hand-curated featured atlas cards, preserved
EQUATION_LIB       knowledge.db::equations → ALL 1,241 display-type LaTeX equations
PAASCH             data.seed.js            → 6 mass-spiral sequences, preserved
buildSpectrum, mulberry32                  → preserved (visualization helpers)
```

Final data.js lands around **600 KB**. All 1,241 library equations ship
with their file/line provenance and sentence of context.

## Design decisions

- **Equations stay hand-curated.** The DB has 239,906 equation rows but they're
  mostly `code`/`comment` fragments from script extraction. Only 1,241 are
  `display` LaTeX, and none have stable UX handles like `null_geodesic` or
  `jensen_metric`. The atlas is storytelling; it deserves authored content.

- **Seed gets merged, not replaced.** The hand-curated atlas equations reference
  theorem IDs like `T11`, `T20`, `T40` and gate IDs like `T-ACOUSTIC-40`,
  `CUTOFF-SA-37`. Those IDs don't exist in the live DB (which uses
  `proven_N`), so the generator merges seed constants/theorems/gates as a
  fallback layer. Every variable chip in the Equation Atlas resolves to a
  real constant or theorem, whether live-DB-sourced or seed.

- **Gate filter: real ID shape + balanced session buckets.** The DB's 1,907
  gate rows include extractor noise (markdown fragments like "FI", "SD",
  "FAIL (route-split)") — we require `id GLOB '*-*' AND length(id) >= 8 AND id NOT
  GLOB '* *' AND id NOT LIKE 'PASS%'|'FAIL%'|'INFO%'`. We also interleave 30
  pre-S81 narrative gates with 30 S81+ Level-3 reruns so the inspector doesn't
  drown in `T3-*` reproduction entries.

- **Theorem filter: real session reference + no wrap-prose.** Similar noise
  in the theorems table — we require a `sessions` field matching `Session
  <N>` or `<N><letter>?`, and reject any statement starting with session
  wrap-up markers (`Answer**:`, `Changed**:`, `What it is**:`).

- **`REAL_EDGES` is carried but not yet rendered.** The DB's 63 typed edges
  are gates→constants / theorems→constants, encoding reproduction lineage
  (e.g., `T3-S69-BCS-SURFACE-GRAVITY --reproduces--> Delta_BCS`). Shipping
  the data so a future enhancement can surface "which gates reproduce this
  constant?" in the inspector without re-running the generator.

## Regenerating after knowledge-base updates

```bash
# 1. Rebuild the knowledge index + SQLite DB
#    (/weave --update bundles Phase 1-7: archive/provenance harvest →
#    knowledge-index.json → knowledge.db → data.js → topic pages →
#    routing_manifest.json → path-existence audit. data.js is rebuilt as
#    Phase 4, so this single command already refreshes the console stack.)
/weave --update

# 2. Refresh the four sidecars (NOT in /weave --update; manual rebuild
#    after the underlying knowledge.db has been refreshed). Order is
#    independent — each sidecar reads only knowledge.db and/or specific
#    source files, so they can run in parallel.
"phonon-exflation-sim/.venv312/Scripts/python.exe" tools/viz/console/build_master_inventory.py
"phonon-exflation-sim/.venv312/Scripts/python.exe" tools/viz/console/build_plan_state_diff.py
"phonon-exflation-sim/.venv312/Scripts/python.exe" tools/viz/console/build_theorem_genealogy.py
"phonon-exflation-sim/.venv312/Scripts/python.exe" tools/viz/console/build_chain_of_custody.py

# 3. Hard-refresh the browser
```

No cache is written; every page load re-reads `data.js` (and any sidecar
the active view consumes) off disk.

### When to refresh which sidecar

- `master_inventory.json` — after editing `sessions/framework/registry/falsifier-watchlist.md`
  (new predictions, detector schedule changes, EVOI re-ranks, status updates).
- `plan_state_diff.json` — after a new session lands (new plan corpus +
  verdict ledger pair). The diff is per-session, so adding session N+1
  only changes that session's block.
- `theorem_genealogy.json` — after a new slot×track workshop ladder lands
  (new `session-{N}-s{slot}-*-{track}.md` files) OR after a `/weave --update`
  cycle that adds new `proven_N` theorems with `statement` length 20–400.
- `chain_of_custody.json` — after **any** `/weave --update` cycle, because
  the BFS depends on the edges table. The harvesters at
  `tools/harvest_attribution_edges.py` + `tools/harvest_chain_of_custody_edges.py`
  produce per-session edge .txt files that `/weave --update` Phase 2 ingests;
  re-run the chain-of-custody builder after any phase-2 rebuild.

## Extending

- **Add a constant to the UI:** append to `CONSTANT_WHITELIST` in
  `build_data.py` as `(name, display, tag, note)`. The generator auto-reads
  the value from `canonical_constants.py` and its provenance from
  `PROVENANCE`.
- **Add a new view:** add a builder `buildFoo(root)` in `views.js`, register
  it in the `BUILDERS` table in `index.html`, add a tab to the `.tabs` div.
- **Wire a new data shape:** extend `window.AE_DATA` via `build_data.py` —
  the shape is defined by the template at the bottom of the file.

## Why this exists

From the design-tool chat: "Ultimately, it is a map of physics equations,
tests, and results. And the constants and gates that build the bones of the
project. Since we conceived of it, there was a concept of visualizing the
data — we didn't go very far with it." The static PNGs at `tools/viz/*.png`
were lab-notebook plots. The console is the project seen through its own
eigenmodes.
