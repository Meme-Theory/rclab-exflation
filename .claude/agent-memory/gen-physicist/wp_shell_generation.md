Rule: when generating a WP dispatch shell from an approved per-wave plan, the live template `.claude/templates/workingpaper.md` SUPERSEDES the frozen example `.claude/templates/examples/workingpaper-shell-example.md` wherever they diverge — the example (frozen 2026-04-23, MCP retrofit 2026-04-25) LACKS the `**Output Artifacts**` pending block the template mandates (lines 27-28) and the plan's `wp_section.must_contain` requires. Current practice confirms: S100a shells (`sessions/session-100a/session-100a-w1-workingpaper.md`) carry a COMPACT Output Artifacts pending block naming the concrete per-gate files + must_contain tokens + verdict-line regex.

**Why:** the plan's `output_artifacts.wp_section.must_contain` lists `\*\*Output Artifacts\*\*` for the COMPLETED section; a shell that omits the block forces the runtime agent to invent its placement, and the orchestrator's completion grep then has no anchor. The example's header comment itself documents that it lags retrofits.

**How to apply (COMPUTE / META gate):** per gate = 8-line context header (Status / Gate ID / Trigger / Classification / Agent / Hypothesis-paraphrase / Plan reference) + 4 pending blocks: Output Artifacts (`*(pending — closure-verification checklist mirroring the plan output_artifacts: ... Content presence by regex, never line/byte counts.)*`), MCP Pre-Compute Audit (template-verbatim text), Verdict (`*(pending agent execution)*`), Results — the ONLY `*(pending — include: ...)*` block, naming the plan deliverables (4-tuple with the plan's scheme/convention/L_max pins, sub-criteria/CCs, substitution-chain IDs "with substituted numbers", dual-SHA, artifacts; `[SIGN]` gates add the schema-v2 sign/magnitude/regime 3-tuple row in BOTH the Output Artifacts and Results lists). Gate heading must contain the plan's `section_anchor` as a prefix (append ` (agent-type)` after it — substring grep still matches). Zero `<!-- Runtime agent fills -->` stubs. Footer = `## Wave {W} Synthesis (team-lead)` / `## Carry-Forward Computations` / `## Constraint-Map Updates` / `## Files Produced` with one-line parenthetical placeholders. Preserve INFO-by-design / expected-verdict declarations from the plan in the hypothesis line (e.g. bolded **EXPECTED verdict INFO**) so the runtime agent cannot over-claim a PASS. Verify post-write by grep: anchor count, stub count 0, 3-of-each pending blocks, footer headings.

**Artifact-existence-PASS COMPUTE gate ≠ workshop gate (S118 W0):** a registry-hygiene gate can carry an *artifact-existence-with-content PASS predicate* (the §M1 closure FORM: designated-writer patch landed, must_contain regex matches) and STILL be `gate_type: compute` (COMPUTE-class fallthrough — FAILS M4 because the gate-ID isn't allowlisted). Such a gate DOES emit a verdict line via `emit_verdict` (S117 W0-2 precedent) ⇒ it takes the FULL 4-block stack (Output Artifacts / MCP Pre-Compute Audit / Verdict / Results), NOT the workshop no-verdict-line topology below. **The discriminator is `gate_type` (compute vs workshop/review), NOT the PASS-predicate form.** A spawn prompt may phrase these confusingly ("artifact-existence gates ... NOT a numerical verdict-line block") — read the plan's `gate_type:` + the presence of a `verdict_line:` entry in `output_artifacts:` (with a `^GATE-ID:.* audit_sha256=[a-f0-9]{64}` must_contain) to decide; if both present, full stack. For these, the Output Artifacts checklist names the registry/inventory designated-writer PATCH (+ its section_anchor + must_contain) as a first-class deliverable alongside script/verdict-line/wp_section, and the Results include-block names the determination/branch outcome + 4-tuple (value=artifact-exists(...), L_max=N/A) rather than a numerical value. Carry the plan's grep-verifier canonical-import exemption (pure grep-verifiers: NO `from canonical_constants import`, `python-validate` Check-1 WARN is pre-registered WARN-only) and the `schema_v2_3tuple_required` flag ([AUDIT]/[VERIFY] ⇒ false, no [SIGN] 3-tuple) into the Output Artifacts checklist verbatim from the gate block.

**MIXED-wave delta (WORKSHOP/REVIEW gate alongside a COMPUTE gate; S116 W3):** a `gate_type: workshop`/`review` section has a DIFFERENT closure topology — it closes by **artifact-existence-with-content** (`wave-classification.md §M1`), so it carries NO `**MCP Pre-Compute Audit**` block and NO verdict-line block (a verdict line on a workshop/review gate is a type error per `gate-verdicts.md §"Investigation-Track Canonical Path"`). Shape = header (add a `**Gate type**: workshop` line + `**Agents**` plural + `**Rounds**` for a panel) + **Artifact-Existence Closure Checklist** (pending; phrasing per `investigation-13-w2-workingpaper.md` L139: "closes by artifact-existence-with-content; **NO verdict line, NO MCP Pre-Compute Audit block**"; names the deliverable md at `output_path` + each plan `must_contain` marker — for a workshop the spine is `## R1`/`## R2`/`## R3`/`## Structural Verdict`/`## Wrap-Up`; the extra `Carry-Forward` marker is NOT universal — mirror it ONLY when the plan's `workshop_md.must_contain` lists it, which is iff the workshop SEQUENCES a compute mandate into its sibling (S116 W3, the workshop hands a mechanism-selector to the compute). When the wave's gates are PARALLEL/INDEPENDENT (plan "Decision Point Prerequisites: NONE … parallel-dispatchable", S116 W9), the workshop hands NO mandate, the plan must_contain is the bare 5-marker spine, and adding a spurious `Carry-Forward` marker would make the runtime checklist grep a marker the workshop legitimately never writes → false non-closure. Mirror the plan's exact marker set, never a "typical" superset.) + ONE include-block (name it **Structural Verdict** for a workshop, **Results** for review) = the single `*(pending — include: ...)*` block. The COMPUTE sibling keeps the full 4-block stack. Encode the asymmetry in the WP intro line ("Gate-type mix: workshop ×1 + compute ×1, MIXED wave") so runtime agents don't cross-contaminate closure modes. Verify the asymmetry post-write by grep on the STANDALONE HEADING line `^\*\*MCP Pre-Compute Audit\*\*` (NOT the bare string): workshop section has 0 such heading lines + 0 verdict-line-regex closures; compute section has both. A bare-string `MCP Pre-Compute Audit` grep over the workshop § is NOT 0 — the negation-disclosure "NO MCP Pre-Compute Audit block" is EXPECTED (the W3 sibling carries 1). Keep that negation to ONE line: gate-type line says only "NO verdict line", the Artifact-Existence Closure Checklist line carries the full "NO verdict line, NO MCP Pre-Compute Audit block" (S116 W8 initially double-disclosed on both → 2 in the workshop §; aligned down to 1 to match the W3 sibling). **Count-traps that LOOK wrong but are CORRECT (don't false-alarm re-dispatch):** whole-file bare-string `MCP Pre-Compute Audit` count is a FLOOR of 2× the compute-gate count (heading + Output-Artifacts must_contain self-ref per compute gate) and runs HIGHER with framing prose + workshop negation-disclosures — S116 W8 (2 compute + 1 workshop), after the W3-aligned single-disclosure, totals 6 = 2 headings + 2 self-refs + 1 gate-type-mix intro line + 1 workshop checklist negation, NOT the naive 4. ROBUST invariant (use THIS, not the bare-string count): `grep -cE '^\*\*MCP Pre-Compute Audit\*\*'` == compute-gate count AND 0 such heading lines inside any workshop §; same shape for verdict-line `grep -cE '\^S{N}-W{W}-…-LANDING:'`. `Carry-Forward Computations` count = workshop-md-must_contain ref + workshop include-block ref + the footer heading. Also distinguish the workshop-md marker `## Structural Verdict` (`##`-prefixed, lives in the must_contain list) from the section's own `**Structural Verdict**:` include-block heading (`**`-prefixed) — different grep targets, both present in one workshop section.
